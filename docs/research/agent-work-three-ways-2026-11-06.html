Agent work, three ways

Today one round with an agent crosses five places: the Assign dialog, the work panel on the task, the Feed, the report's own page, and the stream at the bottom of the task. Nothing shows which tasks are being worked on at a glance. Below is the same scenario in the app as built, then three other shapes. Click through each; the rail under the window counts clicks and moves.

The scenario. Project Website relaunch. Claude has published a first draft of the pricing copy and wants a review. Codex is auditing the checkout and ticks steps off as you watch. Claude is waiting for a launch date. One task went idle. In each option: find the ready work, read it, note three sentences, keep one private, send, read the answer, accept.

What each one changes

Today, as built

Reports are pages appended under the task, newest last. Notes go only on the report's own page, each ticked by hand, then a dialog, then one batch. The answer is another report with Point 1, Point 2. State lives in the work panel on each task; the Feed shows a task only when it needs you.

Decisions 20, 23, 24, 25 as written. Deferred 132 (notes in the stream) is the hop you feel.

A · One living result

The agent owns one Result on the task and revises it. Every version is kept and openable from History, so nothing published is lost, but there is one thing to read. A note goes to the agent unless you lock it. Replies land under the note; the sentences the agent touched are marked. State sits beside the title, on the tab, and as a column in Tasks.

Changes 20, 24, 25: "a report never changes" becomes "a version never changes"; batches and point-by-point responses become notes with replies. Risk: the agent must say what changed, every time; a long result makes "What changed" load-bearing.

B · The task is the dashboard

Your sketch. The project or idea page opens with a Work table: every task, agent, state, steps, latest report, with the question or Continue inline. The task splits into breakdown and reports on the left and a side card on the right with state, steps, evidence and the actions. Reports stay immutable pages, embedded newest first, and take notes in place. The send dialog goes; the ticked count on the card is the button.

Smallest change to the model; closes Deferred 132. Risk: the busiest page of the three, and a project with twenty tasks needs the table to fold or filter.

C · Work inbox and review

One Work view for every assigned task, grouped by what needs you. Review is its own screen: the latest version on the left, your notes as a running list on the right, Request changes and Accept in the strip. Replies thread under the notes; the new version marks its changes. Like reviewing a pull request. The Feed shrinks to questions and approvals.

Changes 23 (the Feed grows into Work) and 24, 25 as A. Risk: a second way to read a report, and heavy for a one-paragraph task.

Mixing them

The three options tie on clicks once the report takes notes in place and the dialog goes. What separates them is whether you can see progress without visiting, and whether the answer lands beside your note or as another document to find.

My pick for a first cut: B's Work table on the project page (it is the smallest change and answers "what is being worked on"), A's Result card on the task in place of the stream (one thing to read, replies under the notes, versions behind History), and B's side card for the actions. C's Work view is the right move later if work spans several projects, and the review screen only if results grow long.

Each piece stands alone. The table by itself removes the hunt. The Result card by itself removes the Open, tick and dialog round.
